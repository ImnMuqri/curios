# Slice 7 — Conversation caps Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read the `UsageCounter` that has been incrementing since slice 1, and degrade chat — and only chat — once a page passes its monthly conversation cap.

**Architecture:** A pure rule in `packages/core` holds the cap and the comparison. `chat.service.ts` reads the counter and branches immediately after the pinned-answer lookup and before the gateway call, so free answers keep working and only spend is refused. No schema change, no `Plan` model, no client change.

**Tech Stack:** TypeScript, Prisma 6, Fastify 5, vitest, Postgres.

**Spec:** `devDocs/slice-7-build-spec.md` — read it before Task 1. This plan argues from it, and it corrects two BACKEND.md claims that the plan then implements.

## Global Constraints

- The cap is `FREE_CONVERSATIONS_PER_MONTH = 200`, a named constant in `packages/core`, overridable by env exactly the way `limit()` in `apps/api/src/plugins/rate-limit.ts` does it — same validation, same rejection of a non-integer or a value below 1.
- **No schema change.** No `Plan` model, no new column, no migration. Plans arrive with billing.
- The comparison is `used > cap`, never `>=`. The counter increments *above* the check, so on the Nth conversation `used` is already N; `>=` would deliver 199 of a 200 cap.
- The check sits **after** the `PinnedAnswer` branch and **before** `buildSystemPrompt`/`gateway.chat`. A pinned answer makes no model call and must still be served over cap.
- The check runs on **every turn**, not only when a conversation is created. Gating on `isNew` lets a conversation created over cap reach the gateway on its second turn.
- The over-cap reply yields exactly `{ type: 'text', text }` then `{ type: 'done', conversationId, intent }` — the same pair the pinned branch yields. **No new event type and no client change.**
- The counter keeps incrementing over cap. Refused demand is the volume data the cap number needs.
- `intent` is unchanged over cap: a capped page still offers the capture card.
- Test commands: `pnpm turbo run test --concurrency=1` for the workspace. **Never omit `--concurrency=1`** — the DB-touching packages share one test database and each truncates `"Account" CASCADE`, so in parallel they wipe each other's fixtures and produce failures that move between packages.
- If the test database has just been recreated (a container restart wipes it — it is `tmpfs`), it needs both `prisma migrate deploy` against `DATABASE_URL_TEST` **and** `packages/db/prisma/sql/readonly-role.sql`. Migrations create tables, not roles.

Create `packages/core/src/cap.ts`:

```ts
/**
 * What a page may spend on model answers in a calendar month, counted in
 * conversations rather than messages -- a chatty visitor costs one unit.
 *
 * 200 is roughly seven conversations a day. It is a guess, and the spec says
 * so: slice 1 was right that a cap cannot be chosen without volume data, and
 * wrong that nothing could be built without it. The mechanism does not need
 * the data; only the number does, which is what the override below is for.
 */
export const FREE_CONVERSATIONS_PER_MONTH = 200;

/**
 * The cap in force, letting operations tune it without a deploy.
 *
 * Deliberately the same shape as `limit()` in the API's rate-limit plugin,
 * including refusing a zero: a cap of zero would take every page dark, which
 * is the one outcome BACKEND.md rules out, and failing at boot is louder than
 * serving nothing.
 */
export function conversationCap(): number {
  const raw = process.env.CONVERSATION_CAP_PER_MONTH;
  if (raw === undefined || raw === '') return FREE_CONVERSATIONS_PER_MONTH;
  const parsed = Number(raw);
  if (!Number.isInteger(parsed) || parsed < 1) {
    throw new Error(
      `CONVERSATION_CAP_PER_MONTH must be a positive integer, got ${JSON.stringify(raw)}`,
    );
  }
  return parsed;
}

/**
 * Whether this page has spent its month.
 *
 * `>` and not `>=`, which is the whole of the arithmetic and easy to get
 * backwards. The counter is incremented when the conversation is created,
 * which happens ABOVE the place this is called, so on the Nth conversation of
 * a month `used` already reads N. `>=` would refuse the 200th and deliver 199.
 */
export function isOverCap(input: { used: number; cap: number }): boolean {
  return input.used > input.cap;
}
```

- [ ] **Step 1: Write the failing tests**

Add to `apps/api/src/modules/chat/chat.service.test.ts`, at the end of the file. The helpers used here — `gatewaySaying`, `collect`, `prisma`, and the `nadia` page seeded in `beforeEach` — already exist in this file; read them before writing.

```ts
describe('the monthly cap', () => {
  /**
   * Puts the page at `count` conversations for the current period, without
   * driving that many chats. The period key is `YYYY-MM`, which is what
   * `currentPeriod()` in chat.service.ts produces.
   */
  async function usageAt(count: number) {
    const page = await prisma.page.findUniqueOrThrow({
      where: { handle: 'nadia' },
      select: { id: true },
    });
    const period = new Date().toISOString().slice(0, 7);
    await prisma.usageCounter.upsert({
      where: { pageId_period: { pageId: page.id, period } },
      create: { pageId: page.id, period, count },
      update: { count },
    });
    return page.id;
  }

  const chatSpyGateway = () => {
    const gateway = gatewaySaying('a model answer');
    const spy = vi.spyOn(gateway, 'chat');
    return { gateway, spy };
  };

  it('answers normally below the cap', async () => {
    await usageAt(10);
    const { gateway, spy } = chatSpyGateway();

    const events = await collect(answer({ prisma, gateway }, { handle: 'nadia', question: 'harga?' }));

    expect(spy).toHaveBeenCalled();
    expect(events.some((e) => e.type === 'text' && e.text === 'a model answer')).toBe(true);
  });

  it('spends nothing at all once over the cap', async () => {
    // Asserted against the gateway, not against the reply text. A test that
    // only checked the words would pass against an implementation that called
    // the model and then threw the answer away -- which is the expensive
    // version of this feature.
    await usageAt(500);
    const { gateway, spy } = chatSpyGateway();

    const events = await collect(answer({ prisma, gateway }, { handle: 'nadia', question: 'harga?' }));

    expect(spy).not.toHaveBeenCalled();
    expect(events.some((e) => e.type === 'text')).toBe(true);
    expect(events.some((e) => e.type === 'done')).toBe(true);
  });

  it('still serves a pinned answer over the cap, because it costs nothing', async () => {
    // The argument of this slice. BACKEND.md checked the cap above the pinned
    // branch; a pinned answer makes no model call, so refusing it punishes an
    // owner for having answered the question well.
    const pageId = await usageAt(500);
    await prisma.pinnedAnswer.create({
      data: {
        pageId,
        question: 'Berapa harga?',
        normalizedQuestion: 'harga',
        answer: 'RM95 sekilo.',
      },
    });
    const { gateway, spy } = chatSpyGateway();

    const events = await collect(answer({ prisma, gateway }, { handle: 'nadia', question: 'harga' }));

    expect(spy).not.toHaveBeenCalled();
    expect(events.some((e) => e.type === 'text' && e.text === 'RM95 sekilo.')).toBe(true);
  });

  it('refuses the second turn of a conversation that began over the cap', async () => {
    // The hole that gating on `isNew` would open. The counter only increments
    // when a conversation is created, so a check that ran only there would
    // refuse turn one and then hand turn two to the model for free.
    await usageAt(500);
    const { gateway, spy } = chatSpyGateway();

    const first = await collect(answer({ prisma, gateway }, { handle: 'nadia', question: 'one' }));
    const done = first.find((e) => e.type === 'done');
    const conversationId = (done as { conversationId?: string } | undefined)?.conversationId;
    expect(conversationId).toBeTruthy();

    await collect(
      answer({ prisma, gateway }, { handle: 'nadia', question: 'two', conversationId }),
    );

    expect(spy).not.toHaveBeenCalled();
  });

  it('keeps counting while refusing, because refused demand is the data', async () => {
    // A page recorded as 200 forever says nothing about what a paid tier
    // should cost. A page sitting at 340 in a 200 cap is the argument.
    const pageId = await usageAt(500);
    const { gateway } = chatSpyGateway();

    await collect(answer({ prisma, gateway }, { handle: 'nadia', question: 'harga?' }));

    const counter = await prisma.usageCounter.findFirstOrThrow({ where: { pageId } });
    expect(counter.count).toBe(501);
  });
});
```

```ts
  // The cap, and this is the line where it belongs.
  //
  // Everything above is database work that has already happened -- the
  // conversation row, the message, the question upsert, the pinned lookup.
  // The gateway call below is the only thing that costs money, so the boundary
  // sits exactly where the spend starts. BACKEND.md put this at step 1, above
  // the pinned branch; that predates pinned answers being free, and refusing a
  // free answer because a page has spent too much punishes an owner for having
  // answered the question well.
  //
  // Read on every turn, not only when the conversation is created. The counter
  // increments on creation alone, so a check gated on `isNew` would refuse the
  // first turn of a conversation started over cap and then hand the second to
  // the model for nothing.
  const used = await prisma.usageCounter.findUnique({
    where: { pageId_period: { pageId: page.id, period: currentPeriod() } },
    select: { count: true },
  });

  if (isOverCap({ used: used?.count ?? 0, cap: conversationCap() })) {
    // The same two events the pinned branch yields, so the sheet renders this
    // through a path it already has. `intent` is untouched: a capped page
    // still offers the capture card, because the lead is what the owner is
    // here for and it is worth more when chat has stopped answering.
    const text =
      'We have answered a lot of questions this month and have reached the limit. ' +
      'The answers people ask for most are linked on this page, and you can still ' +
      'reach us using the links above.';
    yield { type: 'text', text };
    await prisma.message.create({
      data: { conversationId, role: 'ASSISTANT', content: text },
    });
    yield { type: 'done', conversationId, intent };
    return;
  }
```

## Self-Review

**Spec coverage.** Every section maps to a task: the constant and the override to Task 1; the placement, the every-turn rule, the off-by-one and the event shape to Task 2; the corrected documents and the walkthrough to Task 3. The spec's "What still counts" is Task 2's fifth test. Its "no `Plan` model" is enforced by the Global Constraints and by the absence of any migration step — worth stating because the natural instinct on a billing-adjacent slice is to add one.

**Placeholder scan.** No TBDs. Every code step carries the code. Task 3 is prose rather than code, so it names the exact sentences to change and the file whose voice to match, rather than saying "update the docs".

**Type consistency.** `conversationCap()`, `isOverCap({ used, cap })` and `FREE_CONVERSATIONS_PER_MONTH` keep their names and shapes from Task 1's Produces block through Task 2's implementation and its import line. The env var is `CONVERSATION_CAP_PER_MONTH` in the implementation, the tests, and the error message.

**One risk worth naming.** Task 2's tests set the counter directly rather than driving 200 conversations, so they prove the comparison and the branch but not that `currentPeriod()` and the upsert agree on the period key. They do agree — both use `toISOString().slice(0, 7)`, and the test computes it the same way — but that is a duplicated derivation, and if `currentPeriod()` ever changes the tests would keep passing against a stale key. The cheap guard is that Task 2's "keeps counting while refusing" test reads back the row the service itself incremented, so a period mismatch would show up there as a count of 1 rather than 501.
